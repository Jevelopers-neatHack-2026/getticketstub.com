# Identity, session, and signed-context model (GT-08)

This page explains the identity and authorization behavior implemented in the application source. It is not an acceptance record or a claim that downstream consumers have integrated with the host. The original architecture audit used `getticketstub.com` main `138e4b9019c0f5a55ad5e3f586d129216b680e4d` (2026-10-12); the app-native landing change did not alter identity routes or shared HTTP helpers. The later signing-key integration from [PR #102](https://github.com/Jevelopers-neatHack-2026/getticketstub.com/pull/102) is described in the signing section below. For route-by-route request fields, limits, errors, and response shapes, see the [HTTP API reference](../api/HTTP-API.md). Current host architecture and integration state are in [CURRENT-STATE.md](CURRENT-STATE.md).

The main implementation is in `src/server/context.ts`, `src/server/context-token.ts`, `src/server/context-modes.ts`, `src/server/project.ts`, the route handlers under `src/app/api/`, and shared origin/error helpers in `src/server/http.ts`. The capability matrix is also exercised by `scripts/smoke-server.mjs` and the offline fixtures under `fixtures/context/`.

## Identity sources and actors

The server derives identity from its own session/device cookies and stored records. A caller-supplied account id, project owner, role, tenant, capability list, correlation id, local-storage value, or decoded share payload does not establish identity or ownership. Routes may accept a project reference such as `stub:<id>` or `event:<id>` as a request to select a resource; the server then checks that scope against its records.

| Actor or role | Meaning in this host | Current use |
|---|---|---|
| Anonymous | No valid session or device identity | Can use explicitly public routes and public link projections; cannot exercise account capabilities. |
| Guest | A server-bound `ts_device` cookie | Can make drafts and use selected guest flows such as art, order creation with an email, and unlisted sharing. Guest identity is not an account. |
| Account | A valid `ts_session` linked to an account row | Can sync its own wall, read its own orders, and use account capabilities granted by the matrix. |
| Owner | Account or guest device that owns a stub | Has scoped stub operations; sensitive approval/order-authority operations require a signed-in account. |
| Captain | Account that created an organizer event | Holds event-scoped capabilities issued by the current matrix. |
| Staff | Account whose email is in `ADMIN_EMAILS` | Receives `admin.view`; project access is separate and is not implied by staff status. |
| Member / viewer | Roles represented in the matrix and token shape | Not issued by the current host's invite flow. |

The host uses one account tenant per account and a device-scoped guest tenant. A public share, gift, claim, wall, approval, or order-authorization token carries only its own bounded capability; possession of one does not turn the caller into an account or grant broader access.

## Guest-to-account claim and persistence

A guest device cookie is generated by the server (`ts_device`): random secret, HTTP-only, `SameSite=Lax`, one-year lifetime, and `Secure` in production. The server stores or derives the guest binding from a hash, not from a browser-selected owner id. A guest can create drafts and selected unlisted records, but cannot use account-only wall sync, publish a public wall, create an event, redeem an account claim, or read account orders.

After email-link sign-in on the same browser, the host adopts eligible guest shares into the account. Existing account shares remain associated with that account. Local drafts are written through `POST /api/wall/sync` under the authenticated account; ownership comes from the session, not ids in the submitted body. A guest on another device has a different device cookie and does not inherit the first device's unsynced drafts.

Claim redemption is serialized in SQLite. Repeating a claim as the same account is idempotent; a different account attempting an already-claimed link receives a conflict. The route catalog describes the request and response behavior; the [claim and share architecture](boundaries.md) describes data projections and token boundaries.

## Magic links and sessions

`POST /api/auth/link` creates a random 256-bit link token and stores its hash. A sign-in or email-change link is single-use and expires after 15 minutes. `GET /api/auth/confirm` checks a link without consuming it; the confirmation `POST` consumes it. This separation allows email scanners to fetch the confirmation page without using the link. Email, reason, return path, and optional share token are validated by the route.

Sandbox delivery is controlled by `sandboxMail()` in `src/server/auth.ts`: sandbox display is enabled when `NODE_ENV !== "production"` or `TICKETSTUB_SANDBOX_MAIL === "1"`. It is independent of `TICKETSTUB_RUNTIME_MODE`. When sandbox delivery is disabled and no mail provider key is configured, link issuance returns `503 mail_unavailable`; no link is exposed in that response. Email changes take effect only after the recipient confirms the new address.

The session cookie is `ts_session`: random 256-bit value, HTTP-only, `SameSite=Lax`, path `/`, `Secure` in production, and 90-day expiry. Only a hash of the cookie value is persisted. The `ts_device` guest cookie lasts one year. Signing out removes the current session; `POST /api/auth/signout` with `{ "everywhere": true }` removes all sessions for that account and advances its `membershipRevision`. Account deletion removes the account and its sessions.

## Request protection and resource bounds

Security checks are route-specific. The HTTP API reference is the definitive list for the audited source snapshot. These rules are important when reading individual handlers:

- `checkOrigin` rejects missing or foreign `Origin` values on routes that call it. `/api/art` and `/api/agent` use a foreign-origin check that allows a missing `Origin`; `/api/research` has no `Origin` check in this source snapshot.
- The allowed origin is route-specific only in whether a check runs; when it runs, it compares against the exact trusted origin. Public deployments must configure a valid, credential-free HTTPS `APP_URL` for that environment. `Host` and forwarded-host/protocol headers never establish authority; with `APP_URL` blank, only a loopback request URL is trusted. Invalid nonempty configuration does not fall back. See the [HTTP origin boundaries](../operations/http-boundaries.md) and the deployment setup below.
- Order-authorization consumer routes use a timestamped HMAC request with `ORDER_AUTH_CONSUMER_KEY`, not the user's session cookie or an `Origin` check. Payment webhook routes use their provider-specific signature verification over the raw body.
- `requireCapability` is used only where the handler needs a capability. It returns a concealed 404 for invisible projects and missing `admin.*`, a 401 when an account is required but the caller has none, and a 403 for an insufficient signed-in role. Public-link routes and some auth, status, research, and signed-consumer routes follow their own rules.
- Many handlers use `readJson()` or another explicit size check; limits vary by route. `/api/art` currently calls `req.json()` and has no explicit route-level request byte ceiling. Its input fields and downstream generation quotas are separate controls.
- The shared `limit()` helper stores fixed-window counters in the Node process. A restart resets counters, and separate instances do not share them. Routes that do not call this helper have no such route-level limit.

For errors, the common `route()` wrapper maps `HttpError` to `{ error: { code, message } }` and unexpected failures to a bounded internal error. Custom verification verdicts, redirects, no-content responses, image bytes, and raw `NextResponse` responses can have different shapes and cache headers. `json()` defaults to `no-store`; this does not mean every response is no-store. An `x-request-id` is a trace id, not a retry key.

## Capability model and concealment

The matrix in `src/server/context-token.ts` is the source of capability grants. An account capability does not imply access to another account's records. For scoped records the server resolves the owner/captain from storage before granting the capability. A missing or inaccessible project can be returned as 404 to avoid disclosing its existence. A caller with a known project but insufficient role can receive 403. Guest or anonymous callers receive 401 for account-only operations.

The application capabilities below repeat `CAPABILITY_MATRIX`, as does [the context fixture reference](../../fixtures/context/README.md#capability-matrix). `scripts/smoke-server.mjs` checks that both references list every application capability; the route and fixture checks establish the actual grants and denials.

| Actor or scoped role | Application capabilities |
| --- | --- |
| Everyone (anonymous, guest, account) | `stub.draft`, `art.generate`, `agent.use`, `share.create`, `share.view`, `wall.public.view`, `claim.view`, `file.read`, `order.create` |
| Signed-in account, any role | The public capabilities plus `account.read`, `account.email.change`, `account.delete`, `session.revoke`, `wall.sync`, `wall.publish`, `order.read`, `event.create`, `claim.redeem` |
| Owner of the selected stub | `stub.read`, `stub.write`, `share.revoke`, `gift.create`; `stub.approve` and `order.authorize` additionally require a signed-in account, even when a guest device owns the stub |
| Captain of the selected event | `event.read`, `event.publish`, `claims.read` |
| Member or viewer of the selected project | `stub.read` for a stub or `event.read` for an event; these roles are modelled and fixture-tested but are not currently assigned by an invitation flow |
| Staff account on `ADMIN_EMAILS` | `admin.view` in addition to ordinary account capabilities; staff status itself grants no access to another account's project |
| No role on the selected project | No project capability; public and ordinary account capabilities still follow the actor's identity |

There are public exceptions by design: a share or gift token can read its own projection; a public-wall token can read the published wall; approval verification and context verification validate signed material; order-authorization consumer routes validate HMAC and the specific signed authorization. Public token possession never creates an account session.

## Signed context versions

`GET /api/context` issues `ticketstub.context/1` by default. `GET /api/context?v=2` requests `ticketstub.context/2`; the optional `project=<kind>:<id>` parameter asks the host to scope the context, and is accepted only after a server-side ownership check. Tokens are short-lived (five minutes) HMAC-signed values. `POST /api/context/verify` is a verifier endpoint; its `/2` form requires the expected audience. The endpoint rechecks live state through the host's live verifier when configured to do so.

Version 2 deliberately changes the identifier and mode representation:

| Field | Version 1 | Version 2 |
|---|---|---|
| Actor and tenant identifiers | Bare legacy identifier shape | Kind-prefixed identifiers such as `account:<id>` and `guest:<id>` |
| Runtime/economic/evidence modes | Single `mode` value | Separate `environment`, `economicMode`, and `evidenceMode` axes |
| Finance capabilities | None | Explicit `finance.*` strings in the producer matrix |

The context verifier recognizes both versions. A version-1 token is not a version-2 token and does not carry finance grants. Version 2 audience, scope, membership revision, expiry, and mode values are checked by its schema/verifier. Tokens that are not checked again by the host can remain usable until their short expiry; downstream consumers must follow their own acceptance and revalidation contract.

`paid_test` in `economicMode` is a key-presence heuristic for configured paid-provider keys. It signals possible spend, not proof that a provider call occurred. The host's `/2` finance grants and `ticketstub.finance-scope-adapter/1` mapping are implemented in producer code and fixtures, but Finance has not accepted the mapping and the current app has no Finance runtime consumer. See [current architecture](CURRENT-STATE.md#cross-repository-integration-state) and the [integration-evals acceptance record](https://github.com/Jevelopers-neatHack-2026/integration-evals/tree/56018576a9450a2bb46aa55ed3b2f9d9ae97e50d) for the authoritative cross-repository state.

Context tokens continue to use `CONTEXT_SECRET` only, with no rotation overlap: replacing it invalidates outstanding context tokens, whose lifetime is at most five minutes. Approval and order-authorization tokens use the separate versioned sets below. `CONTEXT_SECRET`, `APPROVAL_SIGNING_KEYS`, `ORDER_AUTH_SIGNING_KEYS`, `ORDER_AUTH_CONSUMER_KEY` and provider credentials remain server-only; no secret value belongs in a client bundle or evidence record.

## Signing keys (decision 0003 K4)

Each token class has its own key, so one leaked secret can mint only one class ([integration-evals decision 0003](https://github.com/Jevelopers-neatHack-2026/integration-evals/blob/main/planning/decisions/0003-owner-delegated-decisions-2026-10-12.md), row K4).

| Token | Lifetime | Key | `kid` |
| --- | --- | --- | --- |
| `ticketstub.context` | 5 minutes | `CONTEXT_SECRET`: one key, 32+ characters | none |
| `ticketstub.approval` | 7 days | `APPROVAL_SIGNING_KEYS`: versioned key set | in the header |
| `ticketstub.order-authorization` | 15 minutes | `ORDER_AUTH_SIGNING_KEYS`: versioned key set | in the header |

`ORDER_AUTH_CONSUMER_KEY` is not a token key: it signs consumer requests to the order-authorization port only ([order-authorization.md](order-authorization.md)).

**Format.** A key set is one environment variable holding versioned JSON, the same shape as fulfillment-connectors' `FULFILLMENT_TOMBSTONE_KEYSET` with `kid` as the version name (the example is the approval set; the order-authorization set has the same shape, suggested kids `order-auth-g<generation>`):

```json
{"v":1,"keys":[
  {"kid":"approval-g2","state":"active","activatedAt":"2027-01-10T00:00:00Z","key":"<base64url, 32+ random bytes>"},
  {"kid":"approval-g1","state":"retired","activatedAt":"2026-10-12T00:00:00Z","retiredAt":"2027-01-10T00:00:00Z","key":"<base64url>"}
]}
```

- `kid`: 1-64 of `[A-Za-z0-9._-]`. Suggested `approval-g<generation>` and `order-auth-g<generation>`. Kids starting with `fixture` or `sandbox` are reserved and refused.
- `state`: exactly one `active` key, and it is the newest. `retiredAt` is required on a `retired` key and absent on the active one.
- `key`: **must be generated**, 32 random bytes as canonical base64url: `node -e "console.log(require('crypto').randomBytes(32).toString('base64url'))"`. Never a passphrase, a hand-typed value or another secret. The loader can't measure entropy: it refuses only degenerate keys (under 32 or over 1024 bytes, or fewer than 17 distinct byte values, i.e. a repeated byte or a tiny alphabet), and a passphrase or hex text read as base64url passes that check. It also refuses text containing `FIXTURE-ONLY`, a key repeated in the set, and **reuse of another secret**: each entry is compared in both readings (its decoded bytes and the key string as typed) against both readings (the text and its base64url decoding) of `CONTEXT_SECRET`, `ORDER_AUTH_CONSUMER_KEY` and every key string of the other key set. So the same string pasted into two variables is refused.
- At most 16 keys. Timestamps may be at most 5 minutes in the future (clock skew).

**Signing and verifying** (`src/server/keyring.ts`, bound to the environment in `src/server/signing-keys.ts`). The server signs with the active key and writes its `kid` into the token header, `{"alg":"HS256","typ":"ticketstub.approval","kid":"approval-g2"}`. A verifier looks the `kid` up: the active key, or a retired key until `retiredAt` + the class's token lifetime (7 days for approvals, 15 minutes for order authorizations) + 5 minutes. A retired key also refuses a token whose `issuedAt` is after its `retiredAt` + 5 minutes (or unreadable). That catches **accidental** signing after retirement, such as a process that missed the restart. It does **not** contain a compromised key: whoever holds the key can backdate `issuedAt`, and such a token verifies statelessly until `retiredAt` + lifetime + 5 minutes. A compromised key must be **deleted from the set at once** (see incident rotation below). For approvals and order authorizations, the issuer's verify ports also reject any token whose record differs from the stored one. A missing or malformed `kid` is `unknown`; an unknown `kid`, or a retired key past that window, is `forged`. The `typ` check and the separate keys mean no token class verifies as another, and a token signed with `CONTEXT_SECRET` or another class's key is `forged`.

**Failure modes.**

| `APPROVAL_SIGNING_KEYS`, `ORDER_AUTH_SIGNING_KEYS` | Live runtime | Other runtimes |
| --- | --- | --- |
| unset or blank | **fail closed**: issuing and listing answer 503 `signing_unavailable`, the verify (and claim, revalidate, lookup) ports answer `forged` | a random per-process key, kid `sandbox`; records say `mode: "sandbox"` (tokens die on restart), like `CONTEXT_SECRET` |
| set but invalid | fail closed, as above | fail closed, as above (a misconfigured secret is never silently replaced) |
| set and valid | records say `mode: "live"` | records say `mode: "sandbox"` |

A refused set logs one line per process, `[signing-keys] APPROVAL_SIGNING_KEYS unavailable: <code>`, where the code is a fixed word such as `weak_key` or `active_count`. Errors and logs never carry a key, a kid or the raw value.

**Rotation** (scheduled every 90 days, as K1, or at once on suspected exposure):

1. Generate a new key (the command above). Write the set with the new entry `active` (next generation) and the previous one `retired`. Set **both the new entry's `activatedAt` and the old entry's `retiredAt` to the moment the new set will be live on every instance**, that is, when the GoDaddy restart in step 2 completes, not the moment you write the JSON. The running process keeps signing with the old key until it restarts, and the retention window and the issued-after-retirement check (which catches accidental late signing, not a compromised key) both count from `retiredAt`. The loader accepts timestamps at most 5 minutes in the future, so pick a time within 5 minutes and restart right away. Keep every other retired entry that is still inside its window.
2. Replace the secret in GoDaddy (Preview and Publish separately; a secret can't be edited in place, so delete, re-add, save, restart). A token the old process signed more than 5 minutes after `retiredAt` is refused, so don't let the restart slip past that.
3. The retired entry must stay in the set until `retiredAt` + the token lifetime + 5 minutes of clock skew: **7 days + 5 minutes** for approvals, **20 minutes** (15-minute token lifetime + 5 minutes) for order authorizations. After that it verifies nothing and `status().purgeableKids` lists it. Remove it at the next rotation.

**Why 20 minutes for order authorizations.** An authorization is valid for 15 minutes from `issuedAt`. The old process may sign one at any moment up to `retiredAt` (plus at most 5 minutes of tolerated clock difference), and a consumer may present it at verify, claim or dispatch-time revalidate any time before it expires. So the old key has to keep verifying until `retiredAt` + 15 + 5 minutes. Removing the retired entry earlier turns those in-flight authorizations into `forged` before their `expiresAt`, mid-claim; the owner can re-issue (the stored record and any committed claim survive), but the consumer sees a failure. The window counts from `retiredAt`, which is why step 1 sets it to the restart time and not the edit time.

Approval tokens are derived from the stored record on demand, so after a rotation the owner's approval list hands out tokens under the new `kid`, and tokens already handed out keep verifying under the old one until they expire. On an incident, retiring the exposed key still lets it verify for 7 days, and the issued-after-retirement check does not help, because the holder can backdate `issuedAt`. To cut it off, delete its entry at once: every outstanding approval token under it then reads `forged`, and owners re-fetch theirs from the list (the approvals themselves are records and survive). The same holds for order authorizations: a deleted key makes its in-flight tokens `forged`, and the owner re-issues (the stored record and any committed claim survive).

## Public projections, revocation, and side effects

Stubs are private until explicitly shared. `publicStub` in `src/server/project.ts` rebuilds a projection from an allowlist; private notes, guest lists, photos, claim-set data, ticket/barcode fields, and account details are excluded. Public projections should not be treated as complete copies of private records.

Share links are unlisted and do not expire by default. The owner can revoke a stub share, making its old token return not-found. Public-wall visibility can be disabled and its token rotated. Gift links are separate, unlisted capabilities; revoking the gift deletes its message. `GET /api/gift/[token]` records the first open (except when the owner reads it), so this GET has a write side effect. `GET /api/health` can also write/read a scratch table during its first storage probe. Do not assume every GET handler is strictly read-only.

Artwork files are content-addressed and can be served publicly by hash with long-lived immutable caching. Stopping a share does not invalidate an already-issued hash URL or remove a cached copy. The file endpoint is not an account-private download API. Retention and public projection details belong in the [HTTP API reference](../api/HTTP-API.md) and current [architecture boundaries](boundaries.md).

## Known limitations

This implementation has important boundaries:

- Rate limits are process-local rather than distributed. They do not provide a multi-instance global quota.
- The `/api/research` handler currently lacks an origin check, caller capability check, and route-level limiter. Treat this as actual source behavior, not a blanket application guarantee.
- `/api/art` has no explicit route-level JSON byte cap. Its per-account/device/IP generation allowances control generation, not request-body size.
- A public deployment with a missing or invalid `APP_URL` cannot satisfy routes that use `checkOrigin`; link-generation paths that need `appOrigin` also refuse untrusted authority. This is a configuration boundary, not proof that the deployed host has the correct value. Only the dated host checklist can confirm environment settings.
- A context or approval token is only as current as the verifier check and its expiry. Consumers must not assume a five-minute token is a durable permission for a later external action.
- The app's current cross-repository integration modes, package pins, and missing consumers are recorded in [CURRENT-STATE.md](CURRENT-STATE.md). Shared acceptance remains owned by [integration-evals](https://github.com/Jevelopers-neatHack-2026/integration-evals/tree/56018576a9450a2bb46aa55ed3b2f9d9ae97e50d); this source description does not close any acceptance item.
